## Findings — blockers

### B1. Safety rails are optional policy data, not code (Part 1 system; Part 2 manager)

- Where: [utils/policy_evaluator.py](../utils/policy_evaluator.py#L76-L120) (`validate_policy` accepts any non-empty `when`), [utils/policy_evaluator.py](../utils/policy_evaluator.py#L240-L271) (`evaluate` has no rail stage).
- Failure scenario (executed, **E**): a one-condition policy is valid and auto-approves fraud `yes`/`Y`/blank, the RF-1073 injection ticket, and a $1,150 signature-dispute ticket. Every protection in the example policy (fraud, notes blank, cap, tenure, idempotency) is there only because the author remembered to write it.
- Business impact: the first manager edit or LLM draft that omits one condition moves real money on fraud and injection cases. Task 02's own design says "rails first (always review; they win)" and "engineers own the vocabulary", but that is not implemented.
- Minimal fix: add a small, hardcoded rail check in `evaluate` before the allow walk. Do not make it policy-optional: fraud must clean to `no`; `request_id` and `customer_id` present; amount parses and is > 0; customer and support notes blank, unless a future structured evidence flag says otherwise; request not duplicated or already paid. Optionally allow the policy to *tighten* rails (for example a global `amount_usd` review ceiling), never loosen them. Add tests that a reason-only policy cannot approve RF-1070, RF-1073, RF-1077, RF-2181, or RF-2182.

### B2. `approve_full` can be returned without a parsed amount and without carrying the amount (Part 1 system, money)

- Where: [utils/policy_evaluator.py](../utils/policy_evaluator.py#L231-L238) (`_result` has no amount), [utils/policy_evaluator.py](../utils/policy_evaluator.py#L268).
- Failure scenario (executed, **F**): with no amount condition, `amount_usd="lots"` and blank `request_id` approve. Even on valid rows the caller must re-parse the raw string to know what to pay, which is a second parser and a drift risk.
- Business impact: an approval of unknown value, not attributable to a request ID. That breaks "treat every approval as moving real money" and makes audit and idempotency impossible.
- Minimal fix: in `evaluate`, always parse the amount (fail → review) and return `approved_amount: Decimal` quantized to 0.01 on `approve_full`. Require a non-blank `request_id` for any approval. Both belong in the B1 rail stage.

### B3. Idempotency lives only in the preview helper, not the decision function (Part 1 system)

- Where: duplicate-ID exclusion is only in [utils/policy_preview.py](../utils/policy_preview.py#L66-L76). In [utils/policy_evaluator.py](../utils/policy_evaluator.py#L215-L228), the already-paid check runs only if the policy includes `request_id_not_already_paid`, and the paid set is whatever the caller supplies.
- Failure scenario: an intake runner that calls `evaluate` per row (as task 01's pseudo-code describes) with a policy lacking that operator pays both copies of RF-2183 (if a wrong_item rule ever exists) or history copies RF-2040/RF-1019/RF-2111. Nothing persists "decided/paid" across runs, so re-running the command on the same file re-approves.
- Business impact: double payment, which is the most direct money loss.
- Minimal fix: make "not already decided" a rail (B1), backed by a tiny append-only local decision log (CSV/JSON/SQLite) keyed by `request_id`. The runner checks and writes it. Treat any duplicate `request_id` within a batch as review. Mark everything as a simulated decision, never a payment.

### B4. Submission deliverables absent (submission)

- `main.py` is empty ([main.py](../main.py)). There is no one-command run on `pending.csv` or a same-schema file, no README (run, API key, architecture, AI-tool example changed or discarded), no reviewer queue, no manager versioning or activation, no click-through demo, no write-up, and no recording. `requirements.txt` lists only unpinned `pandas`; there is no UI dependency yet.
- Task 01's "Implementation evidence" section still records `main.py --policy ...` runner results that the current `main.py` cannot produce. QA flagged this as previous-snapshot evidence. Leaving it unannotated invites a stale claim in the write-up.
- Fix: see next steps. Not a defect in the current slices, but blocks submission.

### H2. Amount parsing is duplicated (drift risk)

- Where: [utils/data_processing.py](../utils/data_processing.py#L15-L21) and [utils/policy_evaluator.py](../utils/policy_evaluator.py#L25-L31), with separate parse functions ([data_processing.py](../utils/data_processing.py#L45-L61), [policy_evaluator.py](../utils/policy_evaluator.py#L138-L159)).
- Today (executed): identical regex, 0 drift on all 272 rows. They already differ in behaviour, though. Only `data_processing` quantizes to 0.01, and only the evaluator accepts numeric inputs and checks `is_finite`.
- Scenario: someone extends one regex (for example to accept `EUR`, or a trailing `.000`) and not the other. Then the processed CSV, the preview, and the evaluator disagree on what a row is worth.

### H3. `stated_reason` aliases `late` and `damaged` are not folded; reason operands are unchecked

- Where: [utils/policy_evaluator.py](../utils/policy_evaluator.py#L162-L163), [utils/policy_evaluator.py](../utils/policy_evaluator.py#L57-L59).
- Executed (inventory, **H**, **I**): history RF rows with `late` (2) and `damaged` (1, RF-2074 per task 01) stay as `late`/`damaged`. Task 00 requires folding to the six dictionary values. A policy can also name a non-existent reason (`chnaged_mind`) and validate.
- Impact: no wrong payment today (unmatched means review). But any future `late_delivery`/`arrived_damaged` rule treats identical customers differently, and a typo'd draft shows the manager "0 affected" instead of "invalid".
- Fix: explicit alias map to the six dictionary values (unknown → `invalid_request`). Validate the `stated_reason` operand against the same six values. Test fixtures that use `fixture_reason_alpha` will need real reason values.

## Planned next step: "build the agent, make the evaluator a tool, transform free text such as the policy notes CSV into policy JSON (the agent will need to clean things up)"

### Fit with the brief

- **Fits** Part 2 manager ("change policy without an engineer") **if** the agent is only a drafter between the manager's sentence or notes and the closed schema. Task 02 already designs this (`draft_policy_from_notes` returning `{policy, assumptions, cannot_express}`).
- **Does not fit** if "make the evaluator a tool" means an intake agent that calls `evaluate` and then acts on tickets. Intake needs no LLM: `evaluate` is called by plain code. An intake agent adds cost, latency, and an injection surface (RF-1073) for zero benefit, and edges towards the "multi-agent runtime as the product" warning in AGENTS.md. Recommend: **no intake agent**. Expose `evaluate` only inside a `preview` tool to the drafting agent.
- **"The agent will need to clean things up"** is a risk if it means the LLM cleans *request data*. Data cleaning must stay deterministic: fraud tokens, reason aliases, amounts, and dates already have parsers, so fix H3 there. The LLM may only "clean" by turning the manager's prose into a schema-valid draft. It must never rewrite CSVs or reinterpret customer rows.
- **Prerequisite:** fix B1 and B2 first. Execution **E** shows that a plausible, schema-valid one-line draft ("never arrived refunds go through") auto-approves fraud, injection, and $1,150 cases. LLM drafting multiplies the chance of such drafts.

### Guardrails

1. **Tools the agent gets:** `get_schema()` (operators, allowed reason values, rail list), `get_current_policy()`, `validate_draft(policy)` → `validate_policy` + duplicate-key check, `preview(draft)` → aggregates only (counts, flipped request IDs, $ newly auto-paid, rows with later chargeback/appeal as a warning column).
2. **Tools it must not get:** `activate`, `write_live`, `approve`, `reject`, `pay`, or file writes outside a `drafts/` folder. Activation is a UI button pressed by the manager, logged with version, before/after pointer, and timestamp.
3. **Structured output only:** `{policy, interpretation: [str], assumptions: [str], cannot_express: [{note_id, text, reason}]}`. Parse with a strict JSON parser (duplicate keys rejected, `parse_float=Decimal`), then `validate_policy`. On any failure, show the error and no draft. Never "repair" by guessing.
4. **`cannot_express`** is mandatory for any note or sentence that needs a fact not in the schema (photo, signature, delivery photo, carrier investigation, stolen-card confirmation, mis-pick confirmation, partial percentages, rejects). The agent must not approximate these with `stated_reason` alone.
5. **Assumptions surfaced** for every number not in the source text (for example "small = ≤ $49", "good customer = tenure ≥ 3"), shown next to the preview, never silently embedded.
6. **Trust boundary:** policy notes are manager-authored, but still pass them as delimited data, not instructions. Never pass `customer_note`/`support_note` or any customer row to the provider without explicit user approval. `preview` returns IDs and aggregates computed locally.
7. **Offline/mock path:** a deterministic mock drafter (canned responses keyed by input) so the demo, tests, and CI run without a key. The key comes from an environment variable (`.env` ignored). The UI labels mock output as mock.
8. **Can only tighten rails:** once B1 exists, the draft schema must not be able to remove rails. Verify with a test.

### How to evaluate drafting quality

- **Golden set** (version-controlled, offline): each of the 7 notes, plus task 02 manager sentences ("anything over $300 comes to us", "stolen-card cases go straight through", "trust Dana", "auto-reject PayPal"), plus adversarial text (an instruction embedded in a note, a request to remove the fraud guard). Each item has the expected outcome: a specific patch, `cannot_express`, or refusal.
- **Metrics:**
  - schema-valid rate;
  - exact condition match against the expected patch;
  - **`cannot_express` recall on unexpressible items (target 100%; any miss is a blocker)**;
  - unsurfaced-assumption count (target 0);
  - **"widening without disclosure"**: the draft's preview approves any request the expected patch would not (target 0);
  - injection-obedience count (target 0).
- **Preview-based check:** for each draft, run the deterministic preview on history and pending, and diff against the expected policy's preview. Any extra auto ID fails the item.
- Report model, prompt version, cost per draft (not per refund decision, because the LLM is not in the decision path; say so in the write-up), and results across repeated runs.
